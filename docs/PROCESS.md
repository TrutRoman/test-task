## Як я працював

Кожну частину я починав з технічного завдання. Там були стек, перелік функцій, принципи коду й порядок роботи. Порядок завжди однаковий:

1. Спочатку короткий план (файли й що в кожному), далі робота лише після мого «ок».
2. Одна частина за раз: бот, потім сайт, потім Unity, потім модель. В Unity ще й поетапно: палітра й середовище, персонаж, UI, звук, пост-обробка.
3. Після кожного етапу запуск і перевірка: реальний вивід команд, а не «має працювати». Бота я перевіряв з двох акаунтів Telegram, сайт у браузері, гру — відкриваючи Unity після кожного етапу.
4. Коміти я робив сам, вручну. Робочий процес: гілка `feature/<назва>` → push → Pull Request → merge у `main` (PR #1–#4).

Принципи коду, які я поставив для всіх частин:

- простий код замість «розумного»;
- без запасних шляхів (fallback): один правильний шлях;
- якщо передумова не виконана (немає токена, змінної `.env`, посилання в сцені), програма одразу падає з помилкою;
- одна відповідальність на функцію;
- мінімум коментарів, тільки там, де логіка неочевидна;
- без зайвих залежностей і фронтенд-фреймворків;
- перед використанням бібліотеки — актуальна документація, а не пам'ять.

Це видно в коді: `config.ts` і `env.ts` кидають помилку при старті без змінної, кожен Unity-скрипт перевіряє посилання в `Awake` і кидає `MissingReferenceException`.

## Частина 1. Telegram-бот (`bot/`)

**Завдання.** Клієнт пише боту, оператор отримує повідомлення й відповідає, а відповідь доходить саме тому клієнту, який писав.

**Що вийшло.** Клієнт надсилає будь-що: текст, фото, файл, голосове. Бот пересилає це оператору і під кожним повідомленням додає службове повідомлення «👤 Ім'я (@username), ID …» з кнопкою «🚫 Заблокувати». Оператор робить reply на переслане повідомлення, і відповідь будь-якого типу йде тому клієнту. В оператора є клавіатура «📊 Статистика», «👥 Останні клієнти», «🚫 Заблоковані» (з кнопкою «✅ Розблокувати»), у клієнта — кнопка «/start». Дані зберігаються в SQLite, тому reply на старі повідомлення працює й після перезапуску.

**Як працює головний механізм** (`bot/src/bot.ts`, `bot/src/db.ts`):

1. Клієнт пише → `client.on("message")` зберігає клієнта (`saveClient`) і перевіряє блокування.
2. `ctx.forwardMessage(OPERATOR_ID)` пересилає повідомлення. Telegram повертає `message_id` пересланої копії в чаті оператора.
3. `saveMessage(forwarded.message_id, sender.id)` записує пару «id пересланого повідомлення → id клієнта» в таблицю `messages`.
4. Оператор відповідає reply → `operator.on("message")` бере `reply_to_message.message_id`, знаходить клієнта через `findClientIdByMessage` і викликає `ctx.copyMessage(clientId)`.

Перевірка «це оператор» зроблена один раз, на рівні маршрутизації: `privateChats.filter(isOperator)` і `privateChats.drop(isOperator)`. Кожен обробник оператора зареєстрований на композері `operator`, тож клієнт, який надішле текст «📊 Статистика», просто напише оператору.

### Ключові рішення

| Рішення | Альтернативи | Чому так |
|---|---|---|
| **grammY** | node-telegram-bot-api, Telegraf | Сучасна бібліотека з хорошими типами TypeScript і документацією; композери (`filter`/`drop`) зручно ділять логіку оператора й клієнта |
| **Long polling** (`bot.start()`) | Webhook | Не потрібні публічна адреса й HTTPS: бот запускається на будь-якому комп'ютері однією командою. Для продакшну краще webhook |
| **Зв'язка через `message_id` пересланого повідомлення в SQLite** | Мапа в пам'яті; визначати клієнта з `forward_from` | Мапа в пам'яті губиться при перезапуску. `forward_from` порожній, якщо клієнт приховав акаунт у налаштуваннях приватності. `message_id` є завжди, а SQLite переживає рестарт |
| **Окреме службове повідомлення з кнопкою** | Кнопка на самому пересланому повідомленні | `forwardMessage` у Telegram Bot API не має параметра `reply_markup`. Тому кнопка в окремому повідомленні, яке відповідає (reply) на переслане |
| **`copyMessage` для відповіді** | `sendMessage` | `copyMessage` копіює будь-який тип (фото, голосове, документ) одним викликом і без підпису «переслано від» |
| **SQLite (better-sqlite3)** | JSON-файл, PostgreSQL | Одна залежність, файл створюється сам, синхронний API простий; PostgreSQL для одного оператора — надмірно |
| **TypeScript без збірки** | Компіляція через `tsc` у `dist/` | Node 24 запускає `.ts` сам (type stripping); `tsc` лише перевіряє типи (`npm run typecheck`) |

### Етапи

1. Перша версія за моїм технічним завданням: пересилання, reply через `message_id`, `/start` з інструкцією окремо для клієнта й оператора, `copyMessage` для фото та інших типів.
2. Перевірка з двох акаунтів: текст і фото від клієнта дійшли оператору, фото-відповідь оператора дійшла клієнту.
3. Друге технічне завдання: клавіатура «/start» для клієнта, клавіатура оператора, статистика (клієнтів, повідомлень усього й за сьогодні), 10 останніх клієнтів, блокування й розблокування, таблиці `clients` і `messages` з тими полями, які я вказав.
4. Інструкція перевірки в README (10 кроків) і журнал `logs/bot.log`.

## Частина 2. Сайт (`web/`)

**Завдання.** Головна сторінка з меню, реєстрація, вхід, особистий кабінет, вихід, адмін-панель зі списком користувачів, доступна лише адміну.

**Що вийшло.** Сайт «WebTest» для умовної IT-школи: бічна панель, плашка статусу («Гість», «Студент», «Адміністратор»), перемикач світлої й темної теми, каталог курсів-заглушок, реєстрація з живими галочками вимог, кабінет, адмін-панель з лічильниками й таблицею користувачів, сторінки помилок 403/404/500.

**Як працює** (`web/src`):

- **Ланцюжок middleware** у `server.ts`: статика → логування запитів → `exposePath` → розбір форми → сесія → `loadUser` → `csrfProtection` → маршрути → 404 → обробник помилок. Express 5 сам передає помилки async-обробників в обробник помилок, тому try/catch у маршрутах не потрібні.
- **Реєстрація** (`routes.ts`, `POST /register`): `readField` бере лише рядкові поля, `normalizeEmail` робить `trim` і нижній регістр, `validateRegistration` перевіряє правила, далі перевірка унікальності email, `bcrypt.hash` (10 раундів), `createUser`, одразу `logIn`.
- **Вхід:** `findUserByEmail` + `bcrypt.compare`. При помилці одне повідомлення «Невірний email або пароль», щоб не підказувати, чи існує такий email.
- **Сесія** (`auth.ts`): у cookie `sid` лише підписаний ідентифікатор сесії (`httpOnly`, `sameSite=lax`, 1 доба), дані на сервері. `logIn` викликає `session.regenerate` (захист від session fixation), `logOut` знищує сесію й cookie.
- **Доступ:** `requireAuth("/login")` для кабінету, `requireAuth("/register")` для курсів, `requireAdmin` повертає 403 усім, крім адміна.
- **CSRF:** `csrfProtection` кладе випадковий токен у сесію, кожна POST-форма повертає його в прихованому полі `_csrf`; без правильного токена буде 403.
- **Валідація** (`validation.ts`) — єдине джерело правил. Ті самі константи передаються в шаблон `register.ejs` через data-атрибути, і `public/register.js` ставить галочки під час введення. Остаточна перевірка завжди на сервері.
- **Адмін** створюється скриптом `npm run seed` з `ADMIN_EMAIL`/`ADMIN_PASSWORD` з `.env`. Повторний запуск оновлює пароль.

### Ключові рішення

| Рішення | Альтернативи | Чому так |
|---|---|---|
| **Express 5 + EJS (рендер на сервері)** | React/Next.js SPA + API | Для кількох сторінок з формами SPA додає збірку й окремий API без користі. EJS — звичайний HTML з вставками, екранування `<%= %>` захищає від XSS |
| **express-session (стан на сервері)** | JWT або підписаний cookie з даними | Сесію можна знищити на сервері при виході; у cookie немає даних користувача. Мінус: `MemoryStore` скидається при перезапуску (свідоме обмеження) |
| **bcrypt, 10 раундів** | argon2, scrypt (`node:crypto`) | Стандарт для паролів, проста API (`hash`/`compare`), сіль вбудована. Обмеження bcrypt на 72 байти пароля враховано у валідації |
| **Власний CSRF-токен** | Пакет csurf | csurf застарів і не підтримується; токен у сесії й порівняння на POST — кілька рядків, без нової залежності |
| **better-sqlite3, prepared statements** | ORM (Prisma, Drizzle), PostgreSQL | Одна таблиця `users`; параметризовані запити (`?`) повністю закривають SQL-ін'єкції; файл БД без сервера |
| **Звичайний CSS на CSS-змінних** | Tailwind, Bootstrap | Без збірки й залежностей; темна тема лише перевизначає змінні в `:root[data-theme="dark"]` |
| **Гостя з кабінету — на вхід, з курсів — на реєстрацію** | Усіх на одну сторінку | Хто йде в кабінет, найімовірніше вже має акаунт; хто йде в курси — новий відвідувач. Варіант обрав я після короткого обговорення UX |

### Етапи

1. Перша версія за моїм технічним завданням: сторінки, bcrypt, сесії, CSRF, серверна валідація, seed адміна, 403 для `/admin`, адаптивний CSS без бібліотек.
2. Редизайн за моїми чотирма брифами (16.10):
   - дизайн Vocabulary Trainer як референс організації простору, але без копіювання й з власною айдентикою IT-школи;
   - контент не скупчений по центру, кнопки входу й реєстрації без дублювання;
   - статус користувача в правому верхньому куті;
   - картки «Курсів» і «Студентів» з прочерками замість вигаданих чисел, курси-заглушки «Курс Тест 1…9»;
   - жовтий блок «Як протестувати сайт»;
   - галочки вимог під час реєстрації, вимоги «ім'я 2–30 символів», «пароль від 8»;
   - посилання «Уже маєте акаунт? Увійти»;
   - вкладка «Курси» з переходом гостя на реєстрацію, перемикач світлої й темної теми.
3. 19.10 — аудит на SQL-ін'єкції (див. «Безпека» нижче).

### Безпека: перевірка на SQL-ін'єкції

19.10 я замовив окремий аудит форм реєстрації й входу на SQL-ін'єкції з конкретними векторами (`'`, `"`, `--`, `;`, `OR 1=1`). Результат:

- **SQL-ін'єкцій немає.** Кожен запит з даними користувача підготовлений (`db.prepare("... WHERE email = ?")`), значення передаються окремо від тексту SQL. Конкатенації в SQL немає ніде, у боті так само.
- На тестовому екземплярі сайту (окрема база, порт 3001) надіслано 8 типових пейлоадів (`' OR 1=1 --`, `admin@…' --`, `' UNION SELECT …`, `; DROP TABLE users; --` тощо): усі входи відхилено (401), таблиця ціла. Ім'я `Robert'); DROP TABLE users;--` збереглося буквально й показується екрановано.
- **Знайдено іншу ін'єкцію — в лог-файл:** символ нового рядка в полі email дає змогу дописати в `web.log` підроблений рядок. Це не SQLi і на дані не впливає, але журналу входів тоді не можна довіряти. **Наразі не виправлено** (див. «Відомі обмеження»).
- Також відзначено: немає обмеження частоти спроб входу (rate limiting).

Код після аудиту не змінювався: виправляти SQLi не було чого, бо параметризовані запити були з першої версії сайту.

**Завдання.** Меню паузи з кнопками «Продовжити», «Завантажити збереження», «Головне меню», «Налаштування»; бажано — сцена з персонажем: ходьба, біг, присідання, стрибок.

**Що вийшло.** Гра «Тестік гейм» (Unity 6000.6.2f1, URP):

- головне меню з камерою, що облітає рівень;
- рівень зі сходами, ящиками для стрибків, тунелем, який проходиться лише присівши, і огорожею;
- low-poly персонаж із процедурною анімацією;
- меню паузи, налаштування гучності й чутливості, швидке збереження F5;
- пастельна палітра з 5 кольорів, процедурні звуки й музика, пост-обробка.

### Підхід: Editor-скрипти замість ручної роботи в редакторі

Сцени, матеріали, меші, спрайти інтерфейсу й звуки не створювалися мишкою в редакторі. Їх генерують C#-скрипти редактора (папка `Assets/Scripts/Editor`). Ти пишеш скрипт, запускаєш його з меню **Tools** або з командного рядка (`Unity.exe -batchmode -executeMethod TestSceneBuilder.Build`), і в проєкті з'являються сцени, моделі, матеріали та звуки.

- `Tools → Generate Audio` синтезує 11 WAV-файлів;
- `Tools → Build Test Scene` будує сцени `MainMenu` і `Game` та вміст `Assets/Art/Generated`;
- `Tools → Apply UI Font` міняє шрифт у готових сценах.

Чому так:

- усе відтворюється з коду, і зміну видно в git як зміну скрипта;
- не треба годинами клікати в редакторі;
- немає зовнішніх ассетів, тож немає питань ліцензій;
- компіляцію й збірку можна перевірити в batchmode.

Цей підхід запропонував чат-асистент Claude, а я поставив його вимогою в технічному завданні («щоб мені не клікати годинами, зроби Editor-скрипт…»). Ручну доводку сцен я залишав за собою.

### Як працює геймплей

- **Рух** (`Player/PlayerController.cs`): `CharacterController.Move`. Напрямок береться відносно камери: `GetMoveDirection` повертає ввід на кут камери по осі Y. Швидкості: ходьба 4 м/с, біг 7, присідання 2 (поля в інспекторі). Персонаж плавно повертається в бік руху (`FaceDirection`).
- **Стрибок і гравітація:** вертикальна швидкість рахується вручну. На землі вона притискає контролер вниз зі швидкістю −2 м/с, щоб `isGrounded` не «мигав». Швидкість стрибка дорівнює `sqrt(2·g·h)`: так персонаж підстрибує рівно на `jumpHeight` = 1,2 м. Удар головою об стелю обнуляє швидкість (`StopAtCeiling`).
- **Присідання:** висота контролера з 2 м стає 1 м, центр зсувається, щоб ноги лишались на землі. Встати можна лише тоді, коли `Physics.SphereCast` угору не знаходить перешкоди (`HasHeadroom`), тому в тунелі персонаж не встає.
- **Камера** (`ThirdPersonCamera.cs`): yaw і pitch від миші, pitch обмежений −20…70°. `SphereCast` від персонажа до камери наближає камеру, якщо між ними стіна.
- **Пауза** (`UI/PauseMenu.cs`): `Time.timeScale = 0` зупиняє фізику й час, але `Update` продовжує працювати. Тому на паузі вимикаються `PlayerController`, `ThirdPersonCamera` і `QuickSave`, а курсор звільняється.
- **Збереження** (`Save/`): F5 → `QuickSave` записує позицію в `save.json` (`JsonUtility`) у `Application.persistentDataPath`. «Завантажити збереження» неактивна, поки файлу немає. Завантаження викликає `Teleport`, який на мить вимикає `CharacterController`, бо інакше той повернув би стару позицію.
- **Налаштування** (`UI/SettingsMenu.cs`, `UI/GameSettings.cs`): гучність — це `AudioListener.volume`, чутливість — множник миші; обидва значення в `PlayerPrefs`. Гучність застосовується ще до завантаження першої сцени (`RuntimeInitializeOnLoadMethod`).
- **Анімація** (`Player/CharacterAnimator.cs`) лише читає `CharacterController` (швидкість, `isGrounded`, висоту) і рухає півоти кінцівок. Так код руху нічого не знає про візуал. Висота стегон рахується з пози ніг, щоб опорна нога стояла на землі. Аніматор піднімає події `Stepped`/`Jumped`/`Landed`, на які підписаний `PlayerAudio`, тож крок звучить саме тоді, коли нога торкається землі.

## Частина 4. 3D-модель стільця (`model/`, `unity/Assets/Models`)

**Завдання.** Нескладна 3D-модель із матеріалами, імпорт в Unity, колайдери, перевірка зіткнень.

**Що вийшло.** Low-poly стілець:

- його будує Python-скрипт для Blender `model/make_chair.py`: шість окремих деталей (сидіння, спинка, чотири ніжки);
- два матеріали, `Wood` і `Fabric`, із кольорами палітри гри;
- фаска 6 мм на ребрах;
- експорт у `chair.blend` і `chair.fbx`.

В Unity `Tools → Setup Chair Test` (`ChairTestBuilder.cs`) імпортує FBX, перевіряє масштаб і осі, створює префаб з окремим `BoxCollider` на кожній деталі та сцену `CollisionTest`. У цій сцені на сидіння падають чотири куби з `Rigidbody`, а персонаж із гри впирається в стілець.

**Мої вимоги до моделі** (з технічного завдання):

- реалістичні пропорції: сидіння приблизно 0,45 м від підлоги, загальна висота приблизно 0,9 м;
- окремі об'єкти для кожної деталі;
- low-poly з плоским затіненням;
- злегка скошені краї: Bevel з малою кількістю сегментів;
- два матеріали з кольорами з `Palette.cs`;
- застосовані трансформації, origin у центрі основи;
- кілька `BoxCollider` замість `MeshCollider`;
- тестова сцена з кубами, що падають, і з персонажем.

### Як працює

- **Blender** (`make_chair.py`):
  - кожна деталь — куб 1×1×1, розтягнутий трансформацією; `transform_apply` записує масштаб і позицію в геометрію, тому origin усіх деталей — центр основи стільця на підлозі;
  - модифікатор Bevel: ширина 6 мм, 2 сегменти, обмеження за кутом;
  - `shade_flat()` дає плоске затінення;
  - кольори читаються регулярним виразом з `Palette.cs` і переводяться з sRGB у лінійний простір, бо Principled BSDF очікує лінійні кольори;
  - `check_dimensions` перевіряє висоту 0,90 м і низ на z = 0, інакше скрипт падає.
- **Експорт FBX:**
  - `axis_forward = -Z`, `axis_up = Y`: Blender використовує Z-up, Unity — Y-up;
  - `bake_space_transform` записує поворот осей у геометрію, тож у Unity в об'єктів немає зайвого повороту −90° по X;
  - `FBX_SCALE_ALL`: 1 м у Blender дорівнює 1 м в Unity при scale 1, а не 100;
  - модифікатори застосовуються, згладжування `FACE`.
- **Unity** (`ChairTestBuilder.cs`):
  - імпорт без камер, світла й автоколайдерів;
  - матеріали FBX підміняються URP/Lit-матеріалами з палітри;
  - `VerifyModel` кидає виняток, якщо в деталі є поворот або масштаб не 1, якщо розмір не 0,44 × 0,90 × 0,42 м або стілець дивиться не вздовж +Z;
  - `AddBoxCollider` бере розміри з меша кожної деталі.

### Ключові рішення

| Рішення | Альтернативи | Чому так |
|---|---|---|
| **Модель скриптом** | Ручне моделювання в Blender | Відтворюваність: розміри, матеріали й експорт описані кодом; після зміни палітри модель перебудовується однією командою |
| **Кілька BoxCollider** | Один convex MeshCollider; non-convex MeshCollider | Деталі — це коробки з фаскою 6 мм, тож бокс збігається з ними з точністю до міліметрів. Convex-оболонка «залила» б простір під сидінням і між ніжками. Бокси — найдешевший і найстабільніший тип контакту. Non-convex MeshCollider не можна ставити на рухомий Rigidbody |
| **FBX** | Імпорт `.blend` напряму; glTF | Unity імпортує `.blend` лише за встановленого Blender на машині; FBX — стандартний формат, параметри осей і масштабу контрольовані |
| **`ContinuousDynamic` для кубів** | Discrete | Куб, що падає з 2 м, за крок фізики проходить більше, ніж 6 см товщини сидіння; безперервне виявлення не дає «пролетіти» крізь нього |

## Що сподобалося і що вдосконалив би

**Найбільше сподобалось** працювати з Unity-грою; загалом було цікаво з усіма частинами, бо мені подобається цим займатися (зі слів автора).

**Що можна вдосконалити** (обмеження, видимі в коді; уточнити, що з цього назвати як свої пріоритети):

- сайт:
  - сесії в окремому сховищі (Redis або БД) замість `MemoryStore`;
  - обмеження частоти спроб входу;
  - екранування переносу рядка в логах;
  - прапорець `secure` для cookie під HTTPS;
- автоматичні тести: зараз є лише перевірка типів і ручні сценарії;
- бот: webhook замість long polling для продакшну;
- гра:
  - збереження не лише позиції (поворот, налаштування рівня);
  - підтримка геймпада в меню;
  - заборона залазити на куби на сидінні стільця (зараз `CharacterController` на них «застрибує» через `stepOffset`);
- шрифт: підключити власний шрифт замість стандартного TMP — механізм заміни в одному місці вже є.

Стек: Next.js + React + Tailwind, Drizzle ORM + PostgreSQL, TypeScript, Node 24.

Мій внесок за історією git: 46 із 61 коміту, зокрема набори слів, адмін-таблиця, форми створення й редагування, імпорт CSV, режим тренування, схема БД на Drizzle, Docker, тести Vitest. Каркас застосунку (layout з бічною панеллю, автентифікація, навігація за ролями) був у стартовому шаблоні практики, і я над ним працював. Підказки під час тієї роботи давав Gemini Pro (зі слів автора).

Що звідти використано в сайті WebTest (зі слів автора; порівняння коду нижче):

### Save Me

[TrutRoman/SaveMe](https://github.com/TrutRoman/SaveMe). Це 2D-гра на Unity (рівні, персонажі Arra й Grus, вороги, бос), командний проєкт: у репозиторії два автори.

Мої коміти — вороги (Gul, OrkBers, OrkShaman), фінальний бос, анімації персонажа Grus і README. Скрипти руху персонажів (`Arra/script/Arra.cs`, `Grus/script/Grus.cs`) і меню паузи (`Pause/script/Pause.cs`) у репозиторії закомічені співавтором. Підказки під час роботи давав Gemini Pro (зі слів автора).

Зі слів автора, звідти частково взято ідеї для руху персонажа. Порівняння коду показує спільні ідеї, а не перенесений код: це різні рушії руху (2D `Rigidbody2D` проти 3D `CharacterController`) і різні системи вводу.

| Ідея | Save Me | Тестік гейм | Що змінено |
|---|---|---|---|
| Ходьба й біг через Shift | `speed = 8f` з Shift, інакше `5f`, рух через `transform.localPosition` | `walkSpeed` 4 / `runSpeed` 7 / `crouchSpeed` 2 у `PlayerController.GetSpeed` | 3D-рух через `CharacterController.Move` відносно камери; швидкості — поля інспектора |
| Стрибок лише на землі | `Input.GetKeyDown(Space) && isGrounded` → `rb.velocity.y = jumpForce`; земля — `Physics2D.OverlapCircle` | `controller.isGrounded && jumpAction.WasPressedThisFrame()` → `sqrt(2·g·h)` | Висота стрибка задається в метрах; власна гравітація; заборона стрибка в присіді |
| Пауза по Esc | `Time.timeScale = 0` + статичний прапорець `isPause`, який перевіряє кожен персонаж | `Time.timeScale = 0` + вимкнення компонентів з одного місця (`PauseMenu.SetPaused`) | Немає глобальних статичних прапорців; Esc через Input System |
| Звук кроків | Таймер з інтервалом (коротший при бігу) | Подія `Stepped` з `CharacterAnimator`, коли нога торкається землі; окремі звуки ходьби й бігу | Крок синхронізований з анімацією |
| Налаштування гучності | `PlayerPrefs` (`gameVolume`) + оновлення гучності кожного `AudioSource` в `Update` | `PlayerPrefs` (`volume`) → один `AudioListener.volume` | Одне місце замість циклу по джерелах |
| Ввід | Старий `Input.GetKey(KeyCode…)` | Input System, project-wide actions | Клавіші налаштовуються в одному файлі |

## Відомі обмеження

- Сесії сайту в `MemoryStore`: після перезапуску сервера всі виходять з акаунтів.
- Cookie без `secure`, бо сайт працює локально по HTTP.
- Немає обмеження спроб входу; перенос рядка в email дає змогу підробити рядок у `web.log` (знайдено аудитом 19.10, не виправлено).
- Автоматичних тестів немає; перевірка — `npm run typecheck` і ручні сценарії з README.
- `Tools → Build Test Scene` перезаписує сцени повністю, тому після ручної доводки сцен його не запускають.
- У сцені `CollisionTest` персонаж може залізти на куби, що лежать на сидінні (`stepOffset` контролера).
- Сцена `CollisionTest` є в Build Settings, але з меню гри не відкривається.
